## 1. 最终结论

天使桥采用独立子域名、独立目录、独立容器和独立数据库部署在现有腾讯云实例上，不迁移、不覆盖原站，也不复用原有 MySQL、Redis 和 MinIO 的数据。

推荐的最终访问结构为：

```text
https://angel.xxpeople.com/       天使桥 Next.js 前端
https://angel.xxpeople.com/api/   天使桥 Node.js 后端
```

前后端使用同一 HTTPS 域名，通过 Nginx 按路径反向代理。这样可以减少 DNS、证书和跨域配置，浏览器也不会直接访问后端容器端口。

原有站点继续使用原有域名和服务器，保持不变：

```text
xxpeople.com / www.xxpeople.com → 原有服务器和原有站点
angel.xxpeople.com              → 天使桥服务器
```

本文不记录服务器公网 IP、SSH 私钥、数据库口令或 API Key。部署时从腾讯云控制台和服务器私密环境文件读取，避免随公开代码仓库泄露。

上线前必须解决的项目：

1. 生产 API Base 必须使用同源空前缀或完整站点 Origin，不能配置为 `/api`，因为客户端请求路径本身已经包含 `/api`；

因此，本项目可以先部署不依赖豆包的 Fixture 版本，再增量接入豆包并优化前后端；但只有完成 PostgreSQL 恢复验收后，才能满足本文所定义的“部署上线”。

## 4. 安全组现状与本次决定

当前安全组保留：

```text
0.0.0.0/0  ALL  ALLOW
::/0       ALL  ALLOW
```

因此公网实际上可以到达服务器上的所有监听端口，包括现有的数据库、Redis 和 MinIO 端口。80、443 无需再单独放行；此前访问不到它们是因为服务器尚无进程监听，而不是安全组未开放。

本次按团队决定，为避免在黑客松期间改动既有服务器规则，暂时保留 `ALL`。这是主动接受的临时风险，不应描述为安全配置已经完成。

天使桥自身仍遵守以下边界：

- 只有 Nginx 映射宿主机 `80/443`；
- 前端、后端和 PostgreSQL 不单独发布公网端口；
- 数据库凭据只存在服务器私密文件中；
- 不复用既有 Redis、MySQL 和 MinIO；
- 比赛结束后若服务器继续使用，应删除 `ALL`，按实际来源和端口重建规则。

## 7. 数据库实施方案

### 7.1 选择

使用服务器内独立 PostgreSQL 容器，不再采用 Supabase 作为当前部署前提。

原因：

- 服务器资源充足；
- 需要持久化 Demo Session、Consent、Pact、LifeTree 和聊天消息；
- 单机部署可以保持数据、后端和消息状态一致；
- 不需要再维护外部数据库账号和网络依赖。

### 7.2 Migration 与 Repository

已新增并执行聊天 Migration，包含：

```text
conversations
conversation_members
chat_messages
```

聊天表必须保存：

- 会话所属 `session_id` 和 `match_id`；
- 双方 Persona；
- 消息发送者、正文和创建时间；
- 只允许双方 Consent 达到 `mutual_accepted` 后创建会话。

下一步是实现 PostgreSQL Repository，并保持现有 Domain 和 API Contract 不变。HTTP Route 不直接写 SQL，状态判断仍由 Application/Domain 层负责。

### 7.3 备份

第一轮上线至少执行：

```text

部署后：完成一次可读取的 pg_dump
比赛期间：每天一次 pg_dump
```

备份写入：

```text

```

已经生成首份天使桥 PostgreSQL 自定义格式备份，并恢复到临时数据库验证：2 份 Migration、3 个合成场景和 14 张业务/迁移表均可恢复。验证完成后已删除临时恢复库，正式备份以 `600 root:root` 保存在备份目录。

本次没有导出或复制原有 `xxr_mysql` 数据。

## 8. 即时通讯实施方案

### 8.1 当前能力

后端已经提供：

```text
GET  /api/conversations
GET  /api/conversations/:conversationId/messages
POST /api/conversations/:conversationId/messages
GET  /api/conversations/:conversationId/events
```

消息由 POST 接口先写入 PostgreSQL，再通过 SSE 事件流推送给会话双方。只有双方 Consent 达到 `mutual_accepted` 才能读取、发送或订阅该会话。消息与公共匹配池状态在容器重启后仍可恢复。

### 8.2 已部署的黑客松实时版

当前采用：

```text
打开聊天页 → GET /messages 拉取历史
建立连接   → fetch 订阅 /events 并携带 x-demo-role-token
发送消息   → 乐观显示 → POST 写库 → SSE 推送
连接中断   → 1 秒后自动重连 → GET /messages 补齐缺失消息
```

前端显示“实时连接 / 正在重连”状态，并按 `messageId` 去重。Nginx 已对事件路径关闭代理缓冲，将读写超时延长到 3600 秒。后端每 20 秒发送一次 keepalive，避免空闲连接被中间网络提前关闭。

### 8.3 当前边界

当前是单 Backend 实例，SSE 订阅保存在该进程内，不需要 Redis。数据库是消息事实来源，因此重连后可以恢复。只有未来扩展到多个 Backend 实例时，才需要 Redis Pub/Sub 或独立消息中间件；当前不复用 `xxr_redis`。

### 阶段 D1：准备 DNS


不修改根域名和 `www` 记录。

DNS 生效前可以先通过服务器本地 `curl` 和临时 Hosts 验证，不要为测试迁移原站。

### 阶段 D2：生成正式配置

在服务器中：

```bash
cd /srv/angelbridge/deploy
cp compose.application.yaml.example compose.application.yaml
cp nginx/angelbridge.conf.example nginx/angelbridge.conf
```

然后只填写：

- 前后端镜像或构建目录；
- `angel.xxpeople.com`；
- PostgreSQL 数据库名和用户名；
- 服务器私密环境变量路径；
- AI Key（如果本轮真实接入）。

不要把 `/srv/angelbridge/shared/secrets/` 或正式 `.env` 复制回 Git 仓库。

### 阶段 D3：启动基础设施并迁移

顺序必须是：

```text
PostgreSQL
→ 健康检查通过
→ 执行 Migration
→ 导入三个合成场景
→ 后端
→ 前端
→ Nginx HTTP
```

不要使用 `docker compose down -v`，它会删除天使桥数据卷。任何命令都必须在 `/srv/angelbridge/deploy` 下针对天使桥 Compose 文件执行，不能对服务器所有容器进行批量操作。

### 阶段 D4：配置 HTTPS

DNS 生效且 HTTP 健康检查通过后，为 `angel.xxpeople.com` 申请证书，将证书存入：

```text
/srv/angelbridge/shared/certs/
```

随后启用 HTTPS Nginx 配置：

```text
80  → 301 跳转 HTTPS
443 /      → frontend:3000
443 /api/  → backend:8787
```

前端请求路径本身已经包含 `/api`。生产环境应使用同源空前缀，或将 `NEXT_PUBLIC_ANGELBRIDGE_API_BASE` 设置为完整站点 Origin（例如 `https://angel.xxpeople.com`）；禁止再配置为 `/api`，否则会形成 `/api/api/...`。不要把服务器公网 IP 或容器端口写进浏览器代码。

### 阶段 D5：上线验收

按顺序验证：

1. `https://angel.xxpeople.com/` 能打开最终前端；
2. `/api/health` 返回成功且数据库可用；
3. 创建 Demo Session；
4. 心愿整理、Intent 激活和 Matching；
5. A/B 分别 Consent；
6. 建立会话并双向发送消息；
7. 编辑并双方确认 Pact；
8. 完成置换后 LifeTree 更新；
9. 容器重启后 Session 和聊天仍存在；
10. 原有 `xxr_mysql`、`xxr_redis`、`xxr_minio` 启动时间和重启次数未变化。

## 10. 发布与回滚

每次发布使用独立版本号，例如：

```text
angelbridge-frontend:hackathon-001
angelbridge-backend:hackathon-001
```

服务器的 `releases/` 保存当前和前一版 Compose/环境配置引用，不保存明文密钥。

回滚顺序：

```text
停止接收新操作
→ 数据库备份
→ Compose 镜像标签切回上一版
→ 只重建 frontend/backend/nginx
→ 验证 health 和主流程
```

普通代码回滚不删除 PostgreSQL 数据卷。包含数据库结构变更时，必须使用明确的向前修复 Migration，不能直接回滚到与现有 Schema 不兼容的旧镜像。

原站不在本部署链路中，因此天使桥回滚不应修改 `xxpeople.com`、`www.xxpeople.com` 或原站服务器。

## 11. 资源预算

建议的黑客松初始限制：

| 服务 | CPU | 内存 |

| Nginx | 0.25 核 | 128 MB |
