# 天使桥｜前端继续开发与前后端联调交接文档

> 文档状态：黑客松 MVP 联调基线
>
> 面向对象：前端、UI/UX、产品与后端开发成员
>
> 数据口径：当前人物、资源、位置、匹配、桥约、灵宠对话与成长结果均为合成演示数据
>
> 详细接口请求体与返回值：[天使桥｜本地 Fixture API 联调手册](./天使桥_本地Fixture_API联调手册.md)

## 1. 本轮共同目标

本轮不建设完整的真实用户平台，目标是把已经确定的产品界面与现有后端能力连接起来，形成一条可运行、可复现、可现场演示的闭环：

```text
创建演示会话
→ 此刻首页
→ 向小天表达资源与心愿
→ 用户确认 AI 整理结果
→ 激活意图
→ 获得并理解匹配结果
→ 双方分别表达意愿
→ 编辑并分别确认桥约
→ 完成价值置换
→ Outcome 写回生命树
```

当前成功标准不是“页面数量多”，而是高完成度 UI 最终由真实后端状态驱动，刷新、切换角色和继续操作时仍能得到一致结果。

本轮采用“Frontend UI 专注 + Backend Integration 驱动”的协作方式：

> Backend 负责业务状态、Product ViewModel、API Client、Session/角色管理、真实动作绑定和最终前后端联调。
>
> Frontend 负责设计稿高质量还原、页面与组件、动画、导航、浏览器交互和全部视觉体验。
>
> Frontend 不需要理解 Session、Token、Consent、Pact 等领域状态机，也不负责最终真实 API 接入。

这里强调的是 **Backend-driven business workflow，而不是 Backend-driven UI**。Backend 不负责 CSS、layout、color、typography、animation、modal placement、component hierarchy 或页面视觉设计。

具体技术路线是：

```text
Existing Backend API
→ 复用现有 AngelBridgeClient
→ 薄产品动作门面 api.js / api-client.ts
→ demo-session.js / demo-session.ts
→ Frontend UI
```

本轮不优先新增 BFF 路由。后端主要通过现有 API、类型化 Client、Integration bindings 和可直接展示的 Product ViewModel 承担业务复杂度；前端保留全部视觉、布局、交互和浏览器设备能力。

Owner 边界如下：

```text
Existing Backend API       Backend Owner
AngelBridgeClient          Backend Owner
api.js                     Backend Owner
demo-session.js            Backend Owner
Integration bindings       Backend Owner
Frontend UI                Frontend Owner
UI/UX / Animation          Frontend Owner
```

## 2. 对现有前端仓库的判断

检查对象：<https://github.com/YuchenXiao2026/Angel-Bridge> `main` 分支，基准提交 `367b953c4813a7f5b48ac20fb6502aaedcadef36`。

### 2.1 已有资产

- 产品设计与协作方案；
- 静态产品展示页面和基础样式；
- 灵宠及十二生肖视觉素材；
- OpenAPI 草案和前端联调说明草案；
- 一个零依赖 Node.js 内存 Mock API；
- 健康检查与发布心愿的两个基础测试。

这些内容可以继续用于视觉实现、页面文案、灵宠素材和理解用户体验。

### 2.2 当前尚未形成的能力

- 没有真正的多页面或页面状态流；
- 前端代码中没有 `fetch`、`axios` 等真实 API 调用；
- 静态页面尚未由后端数据驱动；
- 没有 Session 与 A/B 角色管理；
- 没有从匹配、双向确认、桥约到生命树成长的交互闭环；
- 仓库中的 `server.js` 是另一套简化后端，并未与静态页面连接。

因此，当前仓库应视为“视觉与早期 Mock 基础”，而不是已经等待最后联调的完整前端。

### 2.3 对 `server.js` 的处理结论

`server.js` 可以保留作为早期方案参考，但停止继续扩展，不作为正式联调后端。原因是它与当前稳定后端在路由、身份、数据模型和状态机上不同，而且尚未实现：

- 用户确认 AI 整理结果；
- 可解释双向匹配；
- A/B 分别授权；
- 分阶段披露信息；
- 双方确认桥约；
- Outcome 写回生命树。

Frontend 不需要删除已有视觉资产，只需继续形成可绑定的新页面和交互；Backend Owner 后续将它们接入统一 Session API。

## 3. 唯一联调基线

后端基线：`Violet-Yui/AngelBridge` 的 `backend` 分支，checkpoint `9c5af79`。

当前基线已经通过：

- TypeScript 类型检查；
- 13 个测试文件、54 个测试；
- ParseResult、MatchProof、BridgePact 和三个演示案例 Fixture 校验；
- 从创建 Session 到 Outcome 写回生命树的 HTTP 闭环。

本阶段遵循以下边界：

1. 后端 Session API 是唯一业务状态来源；
2. 前端产品文案可以继续使用“心愿、资源卡、搭桥、桥约、生命树”；
3. 后端向前端返回适合页面直接渲染的 Dashboard、Match Card、Match Detail、Pact 和 Tree Product ViewModel；
4. 后端负责现有 `AngelBridgeClient` 和薄产品动作门面的主要实现；
5. Backend Integration 通过薄 Client 发送用户动作，不在组件中重新拼装领域对象；
6. 前端不实现匹配算法、流程分支、信息披露规则、双向确认或桥约状态机；
7. 后端不为尚未产生调用的旧 Mock 路由维护第二套接口；
8. 只有真实页面联调证明现有 API 过于复杂时，才考虑极少数聚合或命令接口。

### 3.1 先做薄 Client，不先做 BFF

本方案继续使用 `/api/sessions/:id/...`，不新增一套 `/api/home`、`/api/wishes` 或 `/api/connections` 路由。

现有后端已经包含经过测试的 `src/client/angelbridge-client.ts`。它是底层类型化 HTTP Client，负责 Token Header、响应解包、错误转换和主要 Session 路由。后端下一步是在此基础上交付最多两个前端可用小文件：

```text
api.js / api-client.ts
→ 只负责 HTTP 和产品动作函数

demo-session.js / demo-session.ts
→ 只负责 sessionId、角色 Token、当前角色和 selectedMatchId
```

不重新手写第二套底层 `fetch` 实现，不把所有 Session 状态藏进 `api.js` 全局变量，也不引入复杂前端状态框架。

后端负责：

- 当前处于哪个阶段；
- 当前角色可以看到什么；
- 当前可以执行哪些动作；
- 卡片、详情、待办和成长数据如何转换成 Product ViewModel；
- 动作是否合法以及执行后进入什么状态；
- 合成 Demo 如何初始化、重置和切换视角验证。

Frontend Owner 只负责：

- 页面布局、组件、动画和响应式适配；
- 输入框、选择器、录音、音频播放等设备交互；
- 为按钮、表单、卡片列表提供稳定的数据注入位置和事件入口；
- 完成 loading、成功、空状态、错误和 disabled 的视觉状态；
- 预留 `stage`、`pendingActions` 和 Product ViewModel 的展示位置。

真实 API 调用、Session 恢复、角色 Token 注入、Mock 替换和最终事件绑定由 Backend Owner 在 Integration 阶段完成。

只有出现以下真实问题之一，才允许增加最小 BFF：

- 一个页面首屏必须合并三个以上接口；
- 一个产品动作需要多次写操作，并已经出现部分成功、部分失败；
- 前端不得不复制权限、状态或角色方向判断；
- 多个页面重复实现同一套领域数据转换；
- Tunnel 往返次数已经明显影响现场演示；
- 当前 DTO 无法在不泄露内部结构的情况下表达页面需求。

仅仅为了把 Session 路由改名为旧交接文档中的路由，不构成新增 BFF 的理由。

## 4. 本机联调与远程协作地址

### 4.1 Local Integration

最终前后端本机联调由 Backend Owner 完成。默认环境是：

```text
Frontend localhost
↓
http://127.0.0.1:8787
↓
Backend
```

Backend Owner 本机使用：

```env
API_BASE_URL=http://127.0.0.1:8787
```

公网 Tunnel 不是本机 Integration 或 I1 的前置条件。

### 4.2 Remote Collaboration

只有 Frontend 成员需要异地访问 Backend、团队远程共享、手机访问或提供 Demo preview 时，才启动临时公网 Tunnel：

```env
API_BASE_URL=https://<temporary-tunnel>
```

Frontend 必须预留集中配置 URL 的位置，不得把 `127.0.0.1` 或临时 Tunnel 域名散落在组件中。最终真实地址由 Backend Owner 在 Integration 时配置。

联调前先验证：

```http
GET ${API_BASE_URL}/api/health
```

Quick Tunnel 重启后地址可能变化；变化时只更新集中配置，不修改业务代码。当前后端使用内存 Session，后端进程重启后需要创建新 Session。

## 5. 产品语言与 API 语言对照

| 产品/前端语言 | 后端概念或接口 | 前端理解方式 |
|---|---|---|
| 用户 | Persona、Role Token | 当前无注册流程，是演示场景中的合成角色 |
| 资源卡/我拥有 | `ValueNode(direction=offer)` | 可用于价值置换的资源、能力或服务 |
| 心愿/我需要 | `ValueNode(direction=need)` | 希望获得的资源、服务或机会 |
| 整理表达 | `POST /parse` 或 `pet/turn: organize` | 小天把自然语言整理成候选节点 |
| 意图确认 | `PUT /intent` | 组合 Offer、Need、交换方式、条件和隐私边界 |
| 发布心愿 | `POST /intent/activate` | 用户确认后正式进入匹配阶段 |
| 小天搭桥 | `POST /matches/run` | Hard Gate、双向匹配和排序 |
| 桥指数 | `bridgeIndex` | 匹配卡片的综合展示值 |
| 为什么推荐 | Match Detail 中的 `proof`、`valueToYou`、`valueToOther` | 展示双方价值、证据、满足条件、冲突和未知项 |
| 我愿意了解对方 | `POST /matches/:matchId/consent` | A、B 使用各自 Token 分别决定 |
| 一座桥 | Match Detail + Connection Disclosure | 双方的价值置换关系及阶段性信息 |
| 桥约 | `BridgePact` | 时间、地点、差价、第一步、完成和退出规则 |
| 完成置换 | `POST /pact/finish` | 生成双方 Outcome |
| 生命树成长 | Tree Detail + Outcome | 已完成置换反馈到人生资源与成长记录 |
| 消息/待办 | `GET /inbox` | 当前由服务端状态派生，不建设实时聊天系统 |

## 6. 身份、Session 与角色切换

### 6.1 创建 Session

```http
POST ${API_BASE_URL}/api/demo/sessions
Content-Type: application/json

{"scenarioId":"studio-photography"}
```

推荐首个联调案例：`studio-photography`。

创建成功后，由 Backend Owner 维护的 `demo-session` 保存：

```ts
type DemoClientState = {
  sessionId: string;
  viewerPersonaId: string;
  activePersonaId: string;
  rolesByPersonaId: Record<string, {
    personaId: string;
    token: string;
  }>;
};
```

不要只保存一个 viewer token 和一个固定 candidate token。一个案例可能有多个候选人，应根据所选 Match 的 `candidateId` 找到对应角色 Token。

推荐使用 `sessionStorage`：刷新页面仍可恢复，关闭页面或后端重启后可以方便地创建新 Session，避免 `localStorage` 长期保留失效 Session。

### 6.2 请求身份

除场景列表和创建 Session 外，业务请求统一携带：

```http
X-Demo-Role-Token: <active role token>
```

不使用：

```http
Authorization: Bearer demo_token
```

### 6.3 A/B 演示方式

MVP 推荐 Frontend 提供“切换角色/切换到对方视角”的稳定 UI 入口，由 Backend Owner 绑定真实角色切换：

1. A 使用 viewer token 查看匹配并接受；
2. 根据当前 Match 的 `candidateId` 切换到对应 candidate token；
3. B 重新请求 Dashboard、Match Detail 或 Consent；
4. B 接受后进入桥约；
5. A、B 继续使用各自 Token 分别确认桥约。

切换角色不是只换头像和文案。Backend Integration 每次切换必须更换请求 Token，并重新拉取当前页面数据；Frontend 负责清晰呈现当前身份。

## 8. Backend Integration 必须按顺序接通的主流程

以下顺序是用户操作与后端状态的顺序。每一次关键写操作都必须由明确的 UI 动作触发；后端提供的产品动作门面可以封装同一次确认之后的必要 HTTP 调用，但不能在用户确认前自动发布、接受或确认桥约。操作完成后，Integration bindings 重新读取当前页面 ViewModel 或 Dashboard。

### Step 1：连通与初始化

```text
GET /api/health
→ GET /api/demo/scenarios
→ POST /api/demo/sessions
→ 保存 sessionId 与 rolesByPersonaId
→ GET /api/sessions/:id/dashboard
```

验收：真实 Dashboard 数据驱动“此刻”首页，页面不再读取 `server.js` 的内存数据。

### Step 2：表达与确认

```text
POST /api/sessions/:id/parse
→ 可选 PATCH /nodes/:nodeId
→ POST /nodes/confirm
→ PUT /intent
→ POST /intent/activate
```

注意：发布不是 `parse`、`confirm`、`activate` 三步。`PUT /intent` 不能省略，它承载交换方式、条件与隐私边界。

验收：用户可以看到小天整理结果、进行修改、确认并发布，而不是一句话直接自动发布。

### Step 3：匹配与解释

```text
POST /api/sessions/:id/matches/run
Body: {"mode":"fixture_ai"}
→ GET /api/sessions/:id/matches
→ GET /api/sessions/:id/matches/:matchId
```

验收：展示候选桥、桥指数、双方价值、证据和未知项；不能只展示一个无法解释的百分比。

同一 Session 固定使用 `fixture_ai`。同一模式已有结果时会复用；不要在进入 Consent 后切换 `rule`/`fixture_ai` 模式。

### Step 4：双向意愿

```text
A Token: POST /matches/:matchId/consent {"decision":"accepted"}
→ 切换到对应 candidate Token
B Token: POST /matches/:matchId/consent {"decision":"accepted"}
→ GET /consent
→ GET /connection
```

验收：A 接受后显示“等待对方”，只有 B 也接受才生成桥约。Integration bindings 不能用一次请求代表双方同意。

### Step 5：桥约与成长

```text
GET /pact
→ PATCH /pact
→ A Token: POST /pact/confirm
→ B Token: POST /pact/confirm
→ POST /pact/finish {"outcome":"completed"}
→ GET /tree?view=detail
```

验收：条款在确认前完成编辑；A、B 分别确认；完成后生命树出现 Outcome 和成长反馈。

## 9. API Client 最小职责

Backend Owner 负责交付 Client 的主要实现，并在最终 Integration 时接入 Frontend 工程。底层优先复用已有 `AngelBridgeClient`，不从零维护另一套请求和错误处理。

当前已有浏览器可直接引用的 `FrontEnd/api.js` 与 `FrontEnd/demo-session.js`。Backend Owner 在 Integration 时配置后端地址并绑定页面动作：

```js
import { createAngelBridgeApi } from './api.js';

const api = createAngelBridgeApi({
  baseUrl: 'https://实际联调后端地址',
});
```

Frontend 页面代码不要读取或保存角色 Token；角色与 Session 连续性由 Backend Owner 维护的 `demo-session.js` 管理。

### 9.1 第一阶段公开函数

I1-I3 只暴露 8 个产品动作：

```ts
startDemo()
getDashboard()
organizeWish()
publishIntent()
runMatching()
getMatches()
getMatchDetail()
resetDemo()
```

说明：

| 函数 | 使用场景 | 内部能力 | 角色 | 页面消费 |
|---|---|---|---|---|
| `startDemo()` | 首次进入或重置后重新开始 | `POST /api/demo/sessions` | 无 Token | 保存 Session 和全部角色，进入首页 |
| `getDashboard()` | 首页、角色切换、写操作后刷新 | `GET /dashboard` | 当前角色 | 直接渲染阶段、待办、灵宠、成长和推荐 |
| `organizeWish(text)` | 用户提交自然语言表达 | `POST /parse` | viewer | 渲染 Offer、Need、条件和建议 Intent |
| `publishIntent(draft)` | 用户检查并点击“确认发布” | 节点变更、确认、`PUT /intent`、`POST /intent/activate` | viewer | 成功后刷新 Dashboard；不得在用户确认前调用 |
| `runMatching()` | 用户点击“小天搭桥” | `POST /matches/run`，固定 `fixture_ai` | viewer | 返回候选卡片 |
| `getMatches()` | 匹配页刷新或重新进入 | `GET /matches` | 当前角色 | 渲染当前角色可见候选 |
| `getMatchDetail(matchId)` | 打开“一座桥” | `GET /matches/:matchId` | 当前角色 | 渲染双方价值、证据、未知项和桥指数 |
| `resetDemo()` | 演示重新开始 | `POST /reset` | viewer | 清空前端选中态并重新读取 Dashboard |

`explainMatch()` 第一阶段不单独增加：匹配详情已经包含 Match Proof。需要灵宠口述解释时，再在 I6 调用 `pet/turn: explain_match`。

### 9.3 Client 的通用职责

Client 至少负责：

- 读取 `API_BASE_URL`；
- 从 `demo-session` 获取 `sessionId` 和当前角色；
- 按 `activePersonaId` 注入正确 Token；
- 自动从成功响应中读取 `data`；
- 保留并展示错误响应中的 `error.code` 和 `error.message`；
- 对 URL 中的 `sessionId`、`matchId`、`nodeId` 使用 `encodeURIComponent`；
- 支持切换角色后重新获取数据；
- 不在 Client 内推进业务状态或伪造后端结果；
- 不在 Client 内计算桥指数、筛选候选、判断双方是否达成一致；
- 写操作成功后重新读取后端 ViewModel，不维护一份平行状态机。

### 9.4 Demo Session 状态

采用两个小文件的方案：

```text
api.js / api-client.ts
→ HTTP 与产品动作

demo-session.js / demo-session.ts
→ Demo 上下文
```

`demo-session` 保存：

```ts
{
  sessionId,
  viewerPersonaId,
  rolesByPersonaId,
  activePersonaId,
  selectedMatchId,
  selectedCounterpartId
}
```

建议使用 `sessionStorage`。不要只保存一个固定 `counterpartToken`：一个场景有多个候选，选中 Match 后应根据 `counterpartId` 从 `rolesByPersonaId` 获取正确 Token。

对前端页面可以暴露：

```ts
setRole("viewer" | "counterpart")
getCurrentRole()
```

打开匹配详情时同时保存 `selectedMatchId` 和该匹配的 `selectedCounterpartId`。`setRole("counterpart")` 据此选择具体候选角色；角色切换后重新请求当前页面数据，而不是只切换头像。

成功响应：

```json
{
  "data": {},
  "meta": {
    "requestId": "...",
    "dataMode": "fixture",
    "isSynthetic": true
  }
}
```

错误响应：

```json
{
  "error": {
    "code": "invalid_request",
    "message": "request validation failed"
  }
}
```
