# 天使桥匹配度算法说明

> 版本：Value Connection v0.4  
> 日期：2026-08-29  
> 范围：黑客松 MVP 的真实双用户匹配、解释和后续桥约闭环。

## 1. 核心定义

天使桥匹配的不是两个“相似的人”，也不要求双方必须各自提供一种非金钱资源，而是判断：

> 双方是否都有基于真实档案证据、值得继续沟通的价值理由，并且不存在明确不可调和的冲突。

例如找房：租客获得合适房屋，房东获得租金并找到符合条件的租客。这仍然是双向价值，但不是物物交换。

## 2. 支持的关系模式

一次匹配有一个 `primaryPattern`，可有少量 `supportingPatterns`：

| 模式 | 含义 | 示例 |
|---|---|---|
| `supply_demand` | 一方供给回应另一方需求 | 房源与租房需求 |
| `transactional` | 资源或服务与金钱等对价 | 摄影服务与服务费 |
| `reciprocal_exchange` | 双方资源或技能互换 | 工作室换品牌摄影 |
| `criteria_fit` | 一方属性满足另一方标准 | 岗位与求职者、房东与租客 |
| `collaboration` | 双方能力围绕共同目标组合 | 创业者与技术合伙人 |
| `mutual_affinity` | 兴趣、经历或长期追求适合连接 | 摄影伙伴、同行交流 |
| `gift_support` | 帮助行为或公益目标形成价值 | 经验指导、公益资源支持 |

这些模式是同一套价值连接引擎的不同解释，不是七套独立算法。

## 3. 匹配输入

真实 AI 只接收用户允许用于匹配的内容：

- `match_only` 的资源、需求和目标节点；
- 节点标题、描述、关键词、交付内容和完整度；
- 双方接受的价值置换方式；
- 地点和时间条件；
- 个性标签与兴趣领域标签；
- 匿名 ID 和用于解释的昵称。

不发送：

- `private` 和 `mutual_consent` 节点；
- 手机号、联系方式和精确地址；
- 与本次连接无关的完整人生档案。

## 4. 确定性门槛

确定性代码只排除已经明确的事实冲突：

- 候选是本人；
- 档案尚未激活；
- 双方接受的价值置换方式完全不相容；
- AI 引用了不存在、未授权或属于其他人的节点；
- AI 明确判断任一方没有继续连接的价值；
- AI 返回明确不可调和的冲突。

地点或时间粒度不同不直接淘汰。例如“北京”与“北京朝阳”、“周末”与“周六下午”进入待确认项。旧 Fixture 为保持固定演示排序，仍保留字符串地点和时间门槛；真实用户 AI 路径不使用这项限制。

## 5. AI 结构化评估

豆包使用 `value-connection-v0.4` Prompt 和 Function Calling 返回：

```json
{
  "primaryPattern": "transactional",
  "supportingPatterns": ["criteria_fit"],
  "partyBenefits": [
    {
      "partyId": "viewer-id",
      "strength": "strong",
      "basis": "resource",
      "reason": "房源满足通勤和预算需求",
      "evidenceNodeIds": ["viewer-need", "candidate-offer"],
      "unknowns": ["具体入住日期"]
    },
    {
      "partyId": "candidate-id",
      "strength": "strong",
      "basis": "money",
      "reason": "租客条件符合房东目标且愿意支付租金",
      "evidenceNodeIds": ["viewer-need", "candidate-offer"],
      "unknowns": ["租期"]
    }
  ],
  "executionFit": {
    "level": "partial",
    "reason": "主要条件相符，需确认入住时间和租期",
    "evidenceNodeIds": ["viewer-need", "candidate-offer"],
    "unknowns": ["入住日期", "租期"]
  },
  "matchReasons": [],
  "conflicts": [],
  "confidence": "medium"
}
```

双方受益依据 `basis` 可以是：

```text
resource / money / opportunity / criteria_satisfaction
shared_goal / relationship_value / altruistic_goal
```

## 6. 匹配理由

每个结果返回 1–3 条 `matchReasons`：

1. `value_to_you`：这次连接为当前用户带来什么；
2. `value_to_other`：另一方为什么也值得继续；
3. `execution_fit`：为什么可以开始行动。

证据只够一条或两条时允许少于三条，禁止凑数。每条理由：

- 不超过 45 个中文字符；
- 引用真实节点；
- 不重复匹配百分比；
- 不写“必然成功”“灵魂伴侣”等无证据结论。

当另一方查看同一匹配时，后端交换 `value_to_you` 与 `value_to_other` 的视角，但保留同一个 canonical match 和 Consent 状态。

## 7. 桥梁指数

AI 不直接决定最终百分比。后端把两个 `partyBenefit.strength` 映射为：

```text
exact=1.00, strong=0.84, partial=0.62, weak=0.15, none=0
```

执行度映射为：

```text
clear=1.00, partial=0.70, unclear=0.30
```

单方价值分：

```text
D = 70% × BenefitStrength
  + 20% × ExecutionFit
  + 10% × ConstraintFit
```

双方价值使用调和平均，避免一方很强、另一方几乎无价值时取得虚高分：

```text
B = 2 × D₁ × D₂ ÷ (D₁ + D₂)
M = 1 - 0.15 × |D₁ - D₂|
```

证据置信度：

```text
C = 45% × EvidenceCompleteness
  + 35% × AiConfidence
  + 20% × Freshness
```

最终分数：

```text
BridgeIndex = min(96, round(100 × B × M × (0.90 + 0.10 × C)))
```

任一方为 `none`、双方均为 `weak`，或存在明确 `conflicts` 时不推荐。低于 60 不进入列表，最多返回 3 个候选。

## 8. 标签的作用

### 个性标签

个性标签表示沟通和协作风格，只在价值关系成立后辅助解释和软排序。没有标签不扣分，标签不同不构成冲突。

### 兴趣领域标签

固定 15 项，最多选择 5 项：

```text
公益、社会时政、职场、教育校园、科技
财经、法律、医疗健康、科普、三农
生活家居、亲子、传统文化、摄影摄像、生活记录
```

兴趣标签是 `mutual_affinity` 的主要辅助信号，在其他模式中只是很轻的上下文。它不能替代资源、需求、标准和执行证据。规则路径中个性标签最多影响 6%，兴趣领域最多影响 4%。

## 9. Match Proof 与后续闭环

匹配结果同时返回：

- 关系模式；
- 桥梁指数和档位；
- 1–3 条匹配理由；
- 双方各自获得的价值；
- 已满足条件；
- 明确冲突；
- 待确认项；
- 引用的证据节点。

它继续驱动真实产品流程：

```text
AI 匹配
→ 双方 Consent
→ 实时聊天
→ 生成桥约
→ 双方确认开始
→ 双方确认完成
→ 每人增加 20 成长值
```

## 10. 当前黑客松取舍

- 真实用户使用豆包语义评估；
- 无 AI / Fixture 路径只提供关键词规则基线；
- 当前不做 Embedding、pgvector、多模型路由和排序学习；
- 当前不做招聘、房屋、婚恋等领域专用审核算法；
- 模型失败时明确返回错误，不把 Fixture 伪装成真实 AI；
- 当前优先保证双用户可完成真实匹配—聊天—桥约—成长闭环。

一句话概括：

> 豆包判断双方为什么都值得继续连接，后端用证据、冲突和执行度计算桥梁指数；双向价值成立不等于双方必须交换同一种价值。
