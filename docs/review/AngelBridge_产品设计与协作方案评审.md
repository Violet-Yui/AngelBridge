# AngelBridge｜产品设计与协作方案评审

> 评审对象：[《天使桥 AngelBridge｜产品设计与协作方案》](../product/AngelBridge-产品设计与协作方案.md)  
> 评审视角：产品与前端联合评审。  
> 评审范围：产品定位、MVP 范围、用户流程、页面结构、AI 方案、数据模型、API、技术选型、分工排期和演示表达。  
> 评审目的：减少概念分散和无效开发，形成一条可理解、可操作、可演示的产品主线。

---

## 1. 总体评价

这份方案已经具备较完整的黑客松产品雏形：有明确品牌、有视觉隐喻、有页面拆解、有 AI 能力设想，也包含技术栈、人员分工、排期和演示准备。尤其是“小天”“人生树”“滴水穿石”三组概念，形成了较强的情感记忆点。

目前最需要解决的问题是：**核心过多，但真正完成的用户价值不够集中。**

方案同时希望突出：

- 人生树档案；
- AI 灵宠陪伴；
- 智能匹配；
- 双列信息流；
- 找人、找物与资源交换；
- 社区关系；
- 成长游戏化。

这些概念单独都成立，但在 48 小时 MVP 中同时出现，会让用户和评委难以判断：天使桥首先解决的究竟是什么问题。

建议将整份方案收束为一句产品判断：

> **用户表达自己能提供什么、需要什么，小天帮助他发现一个双方都能获益的连接，并推动双方开始第一次行动。**

人生树、灵宠、信息流和成长分都应服务于这条主线，而不是分别形成新的产品中心。

## 2. 方案中值得保留的部分

### 2.1 品牌与叙事

建议保留：

- “天使桥 AngelBridge”名称；
- “做彼此的天使”核心表达；
- “滴水穿石”对应一次次微小互助的积累；
- 人生树承载个人资源、需要和成长结果；
- 小天作为温暖、主动的人格化 AI 入口。

三者关系应明确为：

```text
小天：帮助用户表达和连接
桥：代表一次双向价值连接
人生树：记录连接带来的长期成长
```

### 2.2 页面拆解方法

方案中的组件树、流程图和页面操作说明比较具体，适合前端直接拆分任务。建议保留这种写法，并为每个页面补充：

- 页面唯一目标；
- 进入条件；
- 主操作；
- 成功状态；
- 空状态；
- 数据来源；
- 演示中是否出现。

### 2.3 灵宠交互

建议保留：

- 小天气泡主动提醒；
- 根据页面和当前状态切换文案；
- 8 秒后收起气泡；
- 快捷问题按钮；
- 简短、温暖、可解释的回复风格。

灵宠的主要职责应限定为：

1. 帮用户整理表达；
2. 播报新机会；
3. 解释为什么合适；
4. 提醒下一步行动。

开放式陪聊可以保留为长期方向，不应成为 MVP 的核心开发量。

### 2.4 工程协作意识

以下规则具有可执行性，建议保留：

- 前端先依据固定 Fixture 开发；
- API Key 只保存在服务端；
- 小步提交，不积压大 PR；
- 主分支始终保持可运行；
- 阻塞超过一定时间立即同步；
- 功能冻结后只修主路径；
- 提前录制备用演示视频。

## 3. 产品定位需要进一步收束

### 3.1 目标用户过于宽泛

“每个人”“找人、找物、资源、闲置、经验、视频”等表达覆盖范围过大，难以在一次演示中证明产品确实解决了某类人的具体困难。

建议 MVP 只选择一个最容易理解的起始场景，例如：

- 空间与创作服务互换；
- 技能与技能互换；
- 项目发起人与协作者连接。

选定场景后，所有页面文案、种子数据、匹配理由和演示脚本都围绕同一个案例。其他场景只用于结尾说明产品可扩展性。

### 3.2 核心痛点没有被单独讲清楚

方案描述了宏大的社会价值，但没有把用户当前最痛的瞬间说透。

建议明确：

> 用户并不是没有资源，也不是没有需求，而是不知道应该向谁表达、不知道谁刚好需要自己能提供的东西，也没有时间在大量内容和关系中逐一寻找。

这样才能自然推出小天的价值：理解、寻找、解释和推进。

### 3.3 产品中心过多

目前人生树、信息流和小天都像首页级产品中心。建议建立主次关系：

```text
第一层：当前要完成的连接
第二层：小天提供的理解与建议
第三层：人生树记录长期成长
```

信息流不应成为另一个独立中心，否则容易分散“精准连接”的产品定位。

## 4. MVP 范围存在的问题

### 4.1 主流程结束得太早

当前主流程在“查看匹配”和“发起意向 Toast”处结束。用户虽然看到了匹配度，却没有真正验证：

- 对方是否也需要用户提供的价值；
- 对方是否愿意连接；
- 双方下一步应该做什么；
- 这次连接是否留下结果。

建议 MVP 至少完成以下最短闭环：

```text
表达拥有与需要
→ 确认 AI 理解结果
→ 查看双向匹配理由
→ 发起连接
→ 对方接受
→ 双方确认第一步行动
```

最终动作可以非常轻量，不需要实现交易和支付，但不能只用 Toast 代替对方状态与行动结果。

### 4.2 Must、Fake、Later 的内容分配不合理

当前方案把信息流、聊天和多个页面列为 Must，却把与价值交换最相关的连接闭环放入 Fake 或 Later。

建议改为 P0、P1、Later，避免“假做”一词影响团队对完成标准的理解。

#### P0｜必须可操作

- 输入一次拥有与需要；
- AI 整理为结构化结果；
- 用户确认或修改；
- 返回少量候选；
- 明确展示双方分别获得什么；
- 发起连接并看到对方决定；
- 双方形成一个明确的第一步行动。

#### P1｜增强体验

- 语音输入和语音回复；
- 人生树三档切换；
- 消息列表；
- 轻量动画；
- 灵宠选择；
- 更多合成案例。

#### Later｜产品愿景

- 公共信息流；
- 点赞、关注、视频频道；
- 复杂交易和支付；
- 多类型灵宠能力差异；
- 长期自动跟进；
- 新闻订阅和广域资源网络。

### 4.3 页面数量偏多

方案计划的信息流、人生树、卡片详情、对话、资料编辑、灵宠选择、消息和我的页，会消耗大量时间在导航与静态布局上。

建议优先完成五个页面：

1. 首页或当前机会；
2. 与小天表达；
3. AI 整理结果确认；
4. 匹配结果与理由；
5. 连接状态与下一步。

人生树可以作为结果页或个人页的一部分。消息、我的、灵宠选择可以使用轻量状态或暂不进入主演示。

## 5. 首次使用流程需要降低门槛

### 5.1 七维资料表单过重

首次打开后要求用户选择灵宠，再填写年龄、情感、身体、财产、技能、能力价值、潜力、梦想、拥有和需要，会形成较高流失风险。

建议改成：

```text
用户先说一句当前愿望
→ 小天追问一到两个必要条件
→ 自动整理出“我能提供 / 我需要 / 我的边界”
→ 用户确认
```

完整人生档案应通过后续使用逐渐丰富，而不是首次进入时一次填完。

### 5.2 表单不应成为唯一数据源

如果用户仍需要手动填写大量字段，AI 会显得只是匹配结果上的附加能力。

建议保留手动编辑作为纠错方式，但主入口应是自然表达。这样用户能够明显感受到：

- AI 理解了非结构化表达；
- AI 主动发现遗漏条件；
- AI 帮助用户把模糊愿望转为可匹配信息。

### 5.3 灵宠选择不应阻塞主流程

灵宠选择具有仪式感，但不是用户获得价值的必要条件。建议：

- 默认直接使用小天；
- 灵宠选择作为稍后的个性化入口；
- 如果时间不足，保留展示页但不放在首次使用必经路径。

## 6. 信息架构与页面交互问题

### 6.1 首页信息层级不明确

双列瀑布流同时展示普通内容、匹配内容、点赞、频道和灵宠提示，会让用户难以确认当前最重要的任务。

建议首页优先级为：

1. 当前最想实现的愿望；
2. 小天找到的少量机会；
3. 当前待确认事项；
4. 其他内容。

如果保留瀑布流，应把它放到“发现”，而不是默认首页。

### 6.2 匹配卡片信息不足

目前卡片强调匹配度和标签，但没有立即回答两个关键问题：

- 对方能给我什么；
- 我能给对方什么。

建议卡片至少包含：

```text
对方提供
对方需要
与你的双向关系
匹配成立的主要条件
仍需确认的一项信息
```

匹配度只能作为辅助信息，不能替代匹配理由。

### 6.3 “去签约”措辞过重

如果页面只是在表达连接意愿，“签约”会让用户误以为已经进入正式合同、交易或法律关系。

建议按状态使用更准确的按钮：

- “我愿意了解对方”；
- “发起连接”；
- “确认下一步”；
- “开始合作”。

只有当双方承诺内容已经明确时，再使用“约定”或“桥约”。

### 6.4 空状态和失败状态缺失

方案主要描述“成功匹配 98%”的理想路径，没有充分说明：

- 用户尚未表达需要；
- AI 理解不准确；
- 没有合适候选；
- 对方拒绝；
- 仍缺少关键条件；
- 网络中断或模型暂不可用。

建议只补充主演示能实际遇到的状态，不需要穷举异常。至少应设计：

- 待完善表达；
- 暂未找到合适连接；
- 等待对方回应；
- 本次未达成，继续寻找。

## 7. AI 产品设计需要加强

### 7.1 AI 当前更像评分插件

当前方案的 AI 主要承担给候选打分和陪聊，用户可能感知不到它为什么是产品不可替代的一部分。

建议 AI 参与三个关键步骤：

1. 把自然语言整理成可匹配结构；
2. 识别双方价值是否互补；
3. 用可验证信息解释匹配理由。

这三个步骤形成连续体验，比单独显示一个高分更能体现 AI 原生。

### 7.2 匹配逻辑只覆盖单向收益

方案中的规则主要验证“对方拥有的是否命中我的需要”，没有明确验证“我拥有的是否回应对方需要”。这更接近商品推荐，而不是价值置换。

建议匹配成立至少满足：

```text
A.need 能被 B.offer 回应
B.need 能被 A.offer 回应
双方接受的交换方式没有冲突
关键时间、地点或交付条件没有明显冲突
```

如果只能满足单向需要，应标记为普通推荐，不应称为双向连接。

### 7.3 匹配度含义不清楚

“98%”容易被理解为成功概率，但方案实际上使用标签和模型判断得到一个排序分。

建议：

- 将名称改为“桥指数”或“适配度”；
- 明确它只用于候选排序，不代表成功概率；
- 同时展示分数依据；
- 不要求模型为了视觉效果强行拉开梯度；
- 没有匹配时允许返回空结果。

### 7.4 LLM 不应独立决定最终结果

让模型直接读取全部候选、输出最终分数和理由，容易产生以下问题：

- 忽略时间、地点等明确条件；
- 理由与原始资料不一致；
- 相同输入多次结果不稳定；
- 很难解释分数来源。

建议采用混合流程：

```text
固定规则先过滤硬条件
→ AI 判断语义互补和交付可行性
→ 固定公式完成排序
→ 输出引用原始字段的理由
```

### 7.5 匹配理由需要证据

当前“对仗句式”适合展示，但仅有一句模板不足以建立信任。

建议详情页同时显示：

- 你需要的内容；
- 对方对应的提供项；
- 对方需要的内容；
- 你对应的提供项；
- 已满足条件；
- 仍需确认事项。

小天的自然语言解释应来自这些字段，而不是重新编造事实。

### 7.6 开放式陪聊优先级偏高

通用陪聊与产品核心关系较弱，也会增加 Prompt、上下文、流式输出和稳定性工作量。

建议 MVP 的对话只支持三个方向：

- “帮我整理刚才的表达”；
- “为什么匹配这个人”；
- “下一步应该确认什么”。

### 7.7 声纹识别建议删除

语音输入可以提升表达自然度，但声纹识别并不是当前主流程所需能力，也会增加生物特征处理和隐私负担。

建议语音只保留：

```text
语音转文字 → AI 理解 → 文本或语音回复
```

## 8. 人生树与成长机制问题

### 8.1 人生树的数据含义需要统一

目前人生树同时承载个人档案、资产列表、需求、潜力、梦想、匹配数量和成长分，容易变成复杂的个人主页。

建议 MVP 只保留四类内容：

- 我能提供；
- 我需要；
- 我正在推动的连接；
- 我已经完成的连接。

年龄、情感、身体、财富等内容不应默认公开，也不应成为所有场景的必填信息。

### 8.2 可见性不能只有整棵树三态

用户可能愿意公开技能，但不愿公开财产；愿意在匹配时展示区域，但不愿直接展示详细地址。

建议至少区分：

- 完全私密；
- 仅参与匹配；
- 匹配成功后展示摘要；
- 双方同意后展示必要信息。

页面应告诉用户：什么信息会在什么阶段被谁看到。

### 8.3 成长分存在错误激励

当前规则奖励填写七维资料和增加“拥有项”，容易鼓励堆积资料，也可能让资源更多的人天然获得更高分。

建议成长分围绕行动，而不是资料数量：

- 完成一次清晰表达；
- 确认自己的提供和需要；
- 回应一次连接；
- 完成一次双方约定；
- 获得一次可信反馈。

需要明确：成长分代表参与和行动进度，不代表人的价值高低。

## 9. 数据模型需要补足业务关系

### 9.1 `ITEM` 模型不足以表达价值交换

方案把资源统一建模为 Item，匹配关系是 `user_id + item_id`。这种结构适合内容或商品推荐，但难以表示：

- 一个人能同时提供多种价值；
- 一个人有多个不同需要；
- 两个人之间哪些提供与需要形成对应；
- 双方接受什么交换方式；
- 哪些条件已经满足、哪些仍待确认。

建议将最小数据对象拆成：

```text
Person：合成角色
ValueNode：一个 Offer、Need 或 Goal
Intent：本次想推动的连接
Match：两个 Intent 之间的双向关系
Decision：每一方的独立决定
Agreement：双方确认的第一步行动
Outcome：本次连接的结果
```

### 9.2 `MATCH` 不应只有一个分数和一句理由

建议匹配结果至少保存：

- 双方 ID；
- 双方对应的 Value Node；
- 排序分；
- 双方分别获得什么；
- 已满足条件；
- 冲突；
- 待确认信息；
- 当前连接状态。

### 9.3 `INTENT` 状态过于简单

只有 `sent` 无法支持对方接受、拒绝、等待和达成。

建议最小状态为：

```text
draft
active
waiting_other
mutual_accepted
rejected
completed
```

状态必须由服务端统一推进，前端只提交用户动作。

## 10. API 契约需要补充的内容

当前九个接口覆盖了信息流、人生树、匹配、聊天和发起意向，但尚未完整支持用户主流程。

建议补充或明确：

- 创建一次独立演示 Session；
- 提交自然语言并获得结构化结果；
- 编辑和确认 AI 整理结果；
- 激活一次匹配意图；
- 获取双向匹配详情；
- 当前用户提交连接决定；
- 查询对方是否已经回应；
- 确认双方第一步行动；
- 查询连接结果和人生树变化。

每个接口需要提供完整示例，而不只是字段摘要：

- 请求 JSON；
- 成功响应 JSON；
- 页面使用的字段；
- 可能返回的业务状态；
- 当前数据是否为演示数据。

前端开发时应有统一请求层，不允许页面各自拼接接口和处理状态。

## 11. 技术方案需要冻结

### 11.1 后端框架仍是二选一

“Hono/Express”仍未形成明确选择。黑客松阶段应只保留一种实现，避免出现两套路由组织方式。

### 11.2 部署路线没有最终闭合

方案同时保留云主机、Caddy、Vercel 前端和云主机后端。建议在开工前明确：

- 前端部署在哪里；
- API 部署在哪里；
- 前端访问 API 的 Base URL；
- 是否需要 HTTPS 和跨域；
- SQLite 文件是否能在目标环境持久化；
- 备用演示如何启动。

### 11.3 SQLite 与 Vercel 不能混用为同一方案

如果后端部署在无状态 Serverless 环境，本地 SQLite 文件不能作为可靠持久化存储。方案需要二选一：

- 云主机 Node 服务 + SQLite；或
- Serverless API + 外部数据库。

### 11.4 AI 服务需要 Provider 边界

产品和前端不应依赖某个模型供应商的专有响应。建议后端统一输出稳定结构，模型更换只发生在服务端 Provider 内部。

---

## 12. 分工和协作风险

### 12.1 后端与产品岗位负载过重

C 同时承担数据库、全部 API、匹配、兜底规则、对话 SSE 和部署；D 同时承担产品、设计、素材、种子数据、PPT、视频和路演。两者都可能成为关键路径瓶颈。

建议：

- 前端成员分别承担一个纵向业务模块，而不只按页面切分；
- 种子数据由产品定义内容，开发成员共同转为可用 Fixture；
- 视觉素材和演示视频明确独立负责人；
- 后端优先完成主流程，聊天 SSE 和扩展 CRUD 后置。

### 12.2 A/B 页面拆分仍可能产生公共组件冲突

“谁先用谁创建共享组件”会造成组件 API 缺少统一设计。

建议在开工前冻结以下公共组件：

- App Shell；
- Tab Bar；
- Button；
- Card；
- Pet Bubble；
- Loading / Empty State；
- Toast；
- API Client。

每个公共组件指定唯一维护者，其他人通过调用和 PR 修改。

### 12.3 API 在第 2 小时完全冻结过早

可以在第 2 小时冻结核心对象和主演示请求，但不必冻结所有实现细节。否则一旦页面验证发现字段缺失，团队可能为了遵守“冻结”而保留错误合同。

建议：

- 第 2 小时冻结对象名称、ID 和主流程；
- 第 6 小时冻结核心 JSON 示例；
- 后续只允许新增可选字段，不随意重命名或删除；
- 每次变更必须同步前端请求层和 Fixture。

### 12.4 缺少纵向联调负责人

方案按职能拆分清楚，但缺少一个负责把“输入—匹配—连接”整体跑通的人。

建议指定一名集成负责人，职责是：

- 维护唯一演示 Session；
- 维护主演示案例；
- 每次合并后运行主流程；
- 记录 P0 阻断；
- 判断某项功能是否影响演示。

## 13. 排期修改建议

当前排期把大量时间投入信息流、静态页和开放式聊天，而真正的连接状态只使用 Toast。

建议调整为四个阶段：

### 阶段一｜冻结体验

- 确认目标用户和主演示案例；
- 确认最短闭环；
- 冻结结构化对象和 Fixture；
- 冻结五个核心页面。

### 阶段二｜并行完成纵向切片

- 前端完成可点击主流程；
- 后端完成结构化、匹配和状态；
- 设计完成核心页面和公共组件；
- 产品完成文案、案例和验收脚本。

### 阶段三｜联调与真实体验

- 输入到结构化确认；
- 确认到匹配结果；
- 匹配结果到双方第一步；
- 结果回到人生树。

### 阶段四｜冻结与呈现

- 只修主路径；
- 手机和投屏测试；
- 连续运行演示；
- 录制备用视频；
- 完成截图、Deck 和提交材料。

时间不足时建议按以下顺序删除：

```text
开放式陪聊
→ 灵宠选择
→ 消息和我的独立页面
→ 发现信息流
→ 生命树动画
→ 语音
```

不应删除：

```text
AI 理解结果确认
双向匹配理由
对方独立回应
双方第一步行动
```

## 14. 演示脚本需要调整

当前脚本主要展示人生树、信息流、高匹配度和流式聊天，最后使用 Toast 表达“去签约”。评委能看到界面和 AI 文案，但不一定能看到价值交换是如何发生的。

建议两分钟演示改为：

| 时间 | 演示内容 | 要证明的产品价值 |
|---|---|---|
| 0:00–0:20 | 用户说出自己能提供和需要什么 | 输入自然、门槛低 |
| 0:20–0:40 | 小天整理并让用户确认 | AI 理解可控，不是黑箱 |
| 0:40–1:05 | 展示 Top 3，打开第一名 | 系统能找到少量相关机会 |
| 1:05–1:30 | 展示双方分别获得什么和待确认项 | 匹配是双向且可解释的 |
| 1:30–1:50 | 发起连接并展示对方接受 | 不是单向推荐或虚假状态 |
| 1:50–2:00 | 展示双方确定的第一步 | 连接能够进入现实行动 |

主演示案例建议使用普通、具体、立即可理解的价值交换，避免依赖宏大履历、高薪 Offer 或复杂身份背景。空间与摄影、产品与开发等案例更容易让评委在十秒内理解双方价值。

## 15. 建议的方案修改清单

### 保留

- 品牌名称与核心 Slogan；
- “滴水穿石”叙事；
- 小天的人格化体验；
- 人生树长期成长隐喻；
- 页面组件树和流程图写法；
- Fixture 并行开发；
- Git 小步协作和备用视频。

### 调整

- 从“所有人和所有资源”收束到一个主演示场景；
- 从信息流首页调整为当前愿望与少量机会；
- 从七维表单调整为自然表达 + AI 整理 + 用户确认；
- 从单向匹配调整为双向价值匹配；
- 从高匹配度展示调整为分数 + 证据 + 未知项；
- 从“去签约”调整为双方独立表达意愿和确认第一步；
- 从按资料数量加成长分调整为按行动成长；
- 从整棵树可见性调整为分阶段、分字段披露；
- 从四个职能孤岛调整为纵向模块协作。

### 删除或后置

- 声纹识别；
- 公共信息流作为 MVP 主线；
- 点赞、关注和视频频道；
- 开放式通用陪聊；
- 首次进入必须选择灵宠；
- 用 Toast 代替对方状态；
- 为了展示效果强制生成高匹配分。

### 开工前必须确定

- 唯一主演示案例；
- 最短用户闭环；
- 五个核心页面；
- 结构化对象与完整 JSON 示例；
- 前后端唯一技术栈；
- 数据与 API 部署位置；
- 公共组件维护人；
- 纵向联调负责人；
- 功能冻结时间和备用演示方案。

## 16. 最终建议

这份方案不需要推倒重来。它已经具备品牌、视觉和执行框架，真正需要的是减少产品中心，把资源集中到一次完整体验：

> **让用户从一句自然表达出发，看到 AI 如何理解自己、如何发现双向价值、如何解释匹配，并最终推动两个人确认一个现实可执行的第一步。**

当这条链路成立后，人生树会自然成为结果的沉淀，小天会自然成为过程中的伙伴，“滴水穿石”也会从一句 Slogan 变成可以被体验的产品机制。
